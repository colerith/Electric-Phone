## 2. 产品目标

将现有楼层前端界面“ta的手机”改造为常驻酒馆页面的脚本版手机，并命名为“电波手机”。脚本加载后在酒馆父页面挂载独立 Vue 界面，不再依赖某个消息楼层中的 iframe；它能够读取当前聊天里由 AI 生成的手机数据，在消息生成、编辑、切换、删除或聊天切换后自动同步。

首版保留原手机的 8 个基础 App：状态、消息、备忘、空间、钱包、日历、浏览、音乐。设置属于系统能力，不计入 8 个基础 App。

## 3. 核心原则

1. **脚本常驻**：切换楼层不会丢失界面，切换聊天时自动重建当前聊天数据。
2. **原格式兼容**：优先兼容现有 `<角色手机>`、`<charN>` 和 8 个 App 标签，不要求已有角色卡立即改写输出格式。
3. **混合事实源**：酒馆正文里的 `<角色手机>`
   数据由当前聊天楼层重建；通过电波手机副 API 独立生成的私聊消息写入当前聊天变量。两类数据均以当前聊天为边界，不进入其他聊天。
4. **不破坏原文**：默认只读取消息，不自动改写历史楼层。隐藏原始标签、安装世界书或正则必须由用户主动触发。
5. **渐进增强**：缺失某个 App 标签时显示空态，其余 App 仍可使用；单段异常不能拖垮整个手机。
6. **视觉统一**：沿用“电波机”的色彩、字体、留白、圆角、轨道与电波装饰，但不照搬 React/Next.js 技术栈。
7. **三层隔离**：所有角色与手机记录按“角色卡 → 聊天文件 → 手机 Char”三级命名空间隔离；任何缓存都不能只用角色名或
   `<charN>` 序号做全局键。
8. **不滥用卡名**：单人卡可自动建立一个默认 Char；一旦识别为多人卡，不得把角色卡名称当作某个 Char 的姓名，也不得为卡名额外制造一个虚假 Char。
9. **组件自有皮肤**：业务界面禁用 h1-h4 与可见的原生 select/radio/checkbox，所有常见控件必须使用电波手机组件；样式以唯一根节点隔离，不受酒馆美化主题影响。
10. **无可见滚动条**：需要滚动的内容保留滚轮、触摸与键盘滚动能力，但不得显示浏览器滚动条。
11. **Char 资料可编辑**：首页提供 Char 信息入口，单人卡自动读取角色卡头像；备注与自定义头像按角色卡和实际 Char 保存，不能破坏聊天级数据隔离。

## 4. 产品形态与入口

### 4.1 脚本项目结构

实现阶段的项目入口为 `index.ts`，项目内不创建 `index.html`。Vue 组件、样式和业务模块可拆分为独立文件，由 `index.ts`
导入并打包。

建议结构：

```text
电波手机/
├─ index.ts                 # 生命周期、宿主挂载、事件注册
├─ App.vue                  # 手机壳与顶层导航
├─ styles.scss              # 传送到酒馆父页面的全局样式
├─ stores/
│  ├─ phone.ts              # 手机与设备状态
│  ├─ chat.ts               # 当前聊天内的会话与消息状态
│  └─ settings.ts           # 全局脚本设置持久化
├─ services/
│  ├─ message-source.ts     # 获取与监听酒馆消息
│  ├─ phone-parser.ts       # 标签解析、校验、合并
│  ├─ identity.ts           # 角色卡/聊天/Char 身份与隔离键
│  ├─ generation.ts         # 主 API / 副 API 生成适配器
│  └─ phone-send.ts         # 手机私聊生成与酒馆发送桥接
├─ prompts/
│  ├─ preset.ts             # 内置模块化提示词
│  └─ schemas.ts            # 各 App 输出协议与校验说明
├─ components/
│  ├─ home/                 # 桌面、组件、Dock
│  ├─ apps/                 # 8 个基础 App
│  └─ common/               # 标题栏、空态、通知等
├─ assets/
│  └─ reference/            # 电波机 UI 参考图，仅开发/验收使用
└─ 需求文档.md
```

### 4.2 酒馆页面挂载

- 脚本在 `$(() => {})` 内初始化。
- 使用带 `script_id` 的唯一容器挂载 Vue，并添加到酒馆父页面 `body`。
- 将脚本 iframe 中生成的样式复制到父页面 `head`。
- 重复加载时先清理旧容器和旧样式，确保单实例。
- `pagehide` 时卸载 Vue、解绑事件、清除定时器并删除挂载节点和传送样式。

### 4.3 用户入口

- 脚本库按钮：“电波手机显隐切换”。
- 脚本库按钮：“重新同步手机数据”。
- 页面提供一个可拖动或固定在安全区内的电波悬浮按钮；点击打开手机，关闭后保留上次位置与当前 App。
- 桌面端显示居中的手机壳弹层；窄屏设备切换为近全屏布局，并避开系统安全区。
- `Esc`、遮罩点击或界面关闭按钮可关闭；执行关闭不销毁已解析数据。
- 打开“消息”时先进入当前聊天文件专属的会话列表；列表中的 Char 只来自该聊天的身份注册表。

## 5. 信息架构

### 5.1 主屏幕

- 顶部状态栏：设备时间、信号、Wi-Fi、电量图标。
- 英雄组件：显示“电波手机”、副标题“爱意化作讯号”、当前角色名/当前终端序号、情绪摘要与电波动画。
- 主要 App 区：状态、消息、备忘、空间；消息图标显示当前聊天内全部私聊线程的未读总数。
- Dock：钱包、日历、浏览、音乐。
- 设置入口：放在主屏幕右上角或系统菜单，不占用 8 个基础 App 的位置。
- 多角色数据存在时，可在英雄组件或终端切换器中横向切换；不再依赖实体 Home 键。

### 5.2 通用 App 导航

- 每个 App 使用统一标题栏：返回、英文眉题、中文标题、可选操作按钮。
- 支持返回主屏幕；是否保留左右翻页和自动轮播由设置控制。
- 页面切换使用 180–360ms 的轻量过渡；遵循 `prefers-reduced-motion`。
- App 内长内容独立滚动，手机壳和酒馆页面不应同时抢夺滚动手势。

## 6. 视觉需求

### 6.1 设计令牌

```text
主深蓝  --wave-navy:  #204075
主雾蓝  --wave-blue:  #5e80be
点缀粉  --wave-pink:  #fc9fbb
正文色  --wave-ink:   #374558
次要色  --wave-muted: #6e7682
纸面白  --wave-white: #ffffff
舞台底色:             #e9edf3 / #edf1f6
```

### 6.2 风格语言

- 背景使用低饱和雾蓝、粉色径向渐变和细微竖向纹理，避免高对比霓虹。
- 卡片为白色或浅蓝粉渐变，配 1px 半透明描边、柔和阴影与 18–34px 圆角。
- App 图标使用粉、蓝、丁香、青绿、灰蓝五组渐变，白色 Font Awesome 图标居中。
- 大标题优先使用思源宋体/中文衬线回退；正文使用苹方、思源黑体或系统无衬线字体。
- 英文眉题使用小字号、大字距、全大写，作为“档案/终端”感的辅助元素。
- 核心装饰包括圆形轨道、信号波形、胶片/票据/档案标签，但装饰不得遮挡信息。
- 默认浅色主题。深色主题可保留为后续增强，首版不因兼容旧设置而牺牲视觉一致性。

### 6.3 尺寸与响应式

- 桌面手机壳目标宽度 390px，最大不超过可视区域；建议宽高比约 1:1.9。
- 移动端宽度不大于 480px 时使用全屏或近全屏布局，取消外部大圆角和重阴影。
- 所有点击目标不小于 40×40px；正文默认字号不小于 12px。
- 不产生横向滚动条；刘海和底部手势区域使用 `env(safe-area-inset-*)` 适配。

## 7. 八个基础 App 需求

### 7.1 状态

输入字段：角色名称、好感指数、性欲指数、情绪气泡、隐秘心声、器官状态。

- 状态页只展示角色名称，不承担稳定身份职责；数据归属必须使用第 9 节定义的
  `char_key`，名称只用于显示和当前聊天内的辅助匹配。
- 好感和性欲显示 0–100 的数值、进度条及括号内描述；越界值展示时钳制到 0–100，但保留原始解析日志。
- 情绪按 `；、，,/` 等分隔为标签。
- 隐秘心声以私密档案卡显示。
- 器官状态按 `【名称】：描述` 拆为卡片；解析失败的行仍以普通状态项展示。
- 多终端时显示未读/数量提示和明确的角色切换入口。

### 7.2 消息

正文兼容输入：普通行 `名字：内容`；以 `【回复】` 开头的行视为当前 Char/手机一侧的回复。电波手机内部私聊采用结构化
`Message` 记录，不再把所有内容压成一行字符串。

#### 7.2.1 会话列表

- 每个当前聊天内的 Char 对应一个独立私聊线程，显示头像、名称、最后消息、时间、未读数、生成中状态和草稿。
- 支持搜索、置顶、免打扰、标记已读；这些状态仅存入当前聊天变量。
- 单人卡首次进入时自动创建唯一默认 Char；同一聊天重复加载不得重复创建。
- 多人卡按实际角色创建多个 Char 与线程，不创建以卡名命名的额外线程。
- 切换聊天文件后立即换成该聊天自己的会话列表；即使是同一张角色卡，也不得共享消息记录、草稿、未读数或乐观消息。

#### 7.2.2 聊天页

- 顶栏显示头像、Char 名称、在线/生成状态、返回和会话设置。
- 普通文字与语音中，User 使用淡粉气泡并靠右，Char 使用淡蓝气泡并靠左；位置、链接、通话和媒体等结构化卡片保持中性表面，只用局部强调色区分发送者。
- 连续同发送者消息可合并头像与间距，但每条消息仍保留独立 ID、状态和操作菜单。
- 进入页面默认定位到最新消息；离开底部时出现“回到最新”按钮。
- 底部输入栏包含语音入口、文本框、扩展按钮和深蓝/雾蓝发送按钮；软键盘弹起时保持可见。
- 生成期间显示“正在输入”和停止按钮；仅锁定当前线程，其他线程仍可查看，但默认不并发生成。
- 允许乐观插入 User 消息；生成失败时保留消息并显示失败、重试和切换 API，不写入酒馆历史楼层。

#### 7.2.3 消息类型

首版消息模型至少支持：

- `text`：纯文本与换行。
- `image` /
  `video`：URL 或本地文件以及简短描述；描述叠放在媒体画面内部，缺少资源时统一使用中性浅灰占位，仅图标跟随发送者强调色。
- `emoji`：Emoji 与表情包分为独立分类；表情包只引用库内已存在的 URL，不由模型编造图源。
- `voice`：文本转写默认折叠，点击展开并播放波形动画；时长由转写长度自动换算，发送端和模型均无需手填秒数。
- `transfer`：金额、币种、备注和
  `pending/received/refunded`（未收款/已收款/已退款）三态；视觉使用近白雾蓝/雾粉票据、蓝色金额和粉色装饰，不使用高饱和整卡底色，仅影响虚构钱包。
- `location`：位置名称与补充说明，使用消息 ID 与地点文本作为种子动态绘制 CSS 示意地图，不读取真实定位。
- `link`：URL、标题、摘要和安全状态；仅允许 `http/https`。
- `call`：语音/视频通话邀请、接听、拒绝、结束与时长，首版为剧情事件卡，不实现真实通话链路。
- `system`：撤回、接收转账、通话结束等不可伪装为普通发言的事件。

#### 7.2.4 扩展面板与弹窗

- 扩展面板按参考图提供：表情、媒体、语音通话、视频通话、转账、位置、分享、刷新。
- 图片/视频面板使用分段控件切换，支持描述和 URL；发送后立即收起，不遮挡聊天页。
- 转账面板包含金额、币种、10 字以内备注与三态选择；必须做金额格式校验。
- 位置弹窗只接收手动文本；不得请求浏览器或设备真实地理位置。
- 分享弹窗支持输入或粘贴链接；解析失败时仍可作为普通 URL 卡发送。
- 表情包面板必须支持：Emoji 独立分类、收藏、分类新建/改名、表情添加/改名、多选删除、按“名称：[URL]”批量解析、文件批量导入和文本导出。
- 每个表情包可标记为全局、User 专属或当前 Char 专属；Char 专属资源以实际 Char key 隔离，切换聊天或 Char 时不得错误显示。
- 语音/视频通话弹窗提供“发起通话”和“通话历史”，未实现真实音视频时明确标注为剧情通话。

#### 7.2.5 消息操作

- 长按或右键菜单包含：编辑、复制、收藏、多选、撤回、引用、转发、删除。
- 多选以触发菜单的第一条消息为选择锚点；每条消息提供“选到这里”，一次选择锚点到目标消息的连续区间，并可快速回到起点或线程末尾。
- 编辑、撤回和删除只操作当前聊天变量中的手机消息；不得改写酒馆正文楼层。
- 引用消息保留被引用消息 ID 和只读摘要；原消息删除后显示“原消息已删除”。
- 转发首版限当前聊天内的其他 Char 线程，复制为新消息并保留来源说明。
- 所有写操作以 `message_id` 保证幂等，重复点击或重试不能产生重复消息/重复扣款。

#### 7.2.6 生成与酒馆桥接

- 默认发送路径为“副 API 独立私聊”：调用
  `generateRaw`，生成结果只写入当前聊天的手机记录，不触发酒馆主 API，也不新建酒馆消息楼层。
- 可选“同步到正文”模式才把自然语言指令追加到酒馆输入框或执行 `/send ...|/trigger`。
- 直接发送正文示例：`给角色名发送消息：你好`。多人卡必须使用实际 Char 名称/ID，不得使用角色卡名称代替。
- 用户可在设置中选择副 API 失败时“保持失败待重试”或“询问后回退主 API”；默认不静默回退主 API。

### 7.3 备忘

- 兼容 `[标题]：内容`、独立 `[标题]` 后接列表、`- 列表项` 与普通多行文本。
- 相邻同标题条目合并为一组档案卡。
- 保留“随性涂鸦”与“涂鸦解析”；三反引号包裹内容去除围栏后展示。
- ASCII 涂鸦使用等宽字体并保留空格和换行；长中文说明与涂鸦主体分区显示。

### 7.4 空间

- 将 `<zone>` 内的“标题：内容”或普通行展示为角色动态/日记卡。
- 头像优先使用角色头像路径，缺失时使用电波渐变占位。
- 展示角色名、稳定生成的短 handle、日期和正文。
- 点赞为当前聊天内的本地 UI 交互，状态存入聊天变量；不得写入全局脚本变量，也不得修改 AI 历史消息。
- 评论与分享按钮首版只在有真实行为时启用，否则以禁用态和说明呈现。

### 7.5 钱包

输入字段：`当前金额`、`购物记录`。购物记录兼容 `- 商品；金额；备注`。

- 顶部展示净资产与币种，支持人民币、日元、美元、欧元、英镑、韩元及常见符号识别。
- 自动判断收支正负并按餐饮、交通、购物、账单、医疗、娱乐、学习、礼物、收入、宠物、旅行、其他分类。
- 每笔交易显示分类图标、商品、备注、金额和时间。
- 无法解析金额时保留原文本，不显示伪造的精确数值。

### 7.6 日历

- 展示最近五天、当前年月和时间轴待办。
- 条目标题解析日期/时间；正文中的 `<s>...</s>` 表示已完成，`[重要]` 表示重点。
- 天气卡不再默认随机生成。若输出格式未提供天气，则展示“天气未知”或隐藏天气卡。
- 纯展示日程不写回聊天；本地完成勾选属于可选增强，需明确与 AI 原始状态的区别。

### 7.7 浏览

- 将 `<browse>` 中条目展示为搜索历史/结果列表。
- 第一条标题或内容作为主要查询词，其余内容作为结果标题与摘要。
- 不随机伪造真实域名、结果数量和耗时；缺失 URL 时显示“本地记录”来源。
- 首版不主动访问外网，不把 AI 文本当作可信链接；只有通过 URL 校验的 `http/https` 地址才可点击。

### 7.8 音乐

输入字段：歌曲名称、歌手名称、精选歌词；歌词用 `/` 分隔。

- 默认采用“电波机”风格的电台/录音终端播放器，保留轨道、波形和歌词轮播视觉。
- 保留 iPod 复古样式作为可选外观。
- 无真实音频 URL 时只作为剧情展示，不伪造正在播放；播放键进入禁用或演示态并给出说明。
- 有受信任音频 URL 后再启用实际播放、进度与暂停状态。
- 歌词高亮可自动轮播，离开页面或卸载时必须清理定时器。

`<char2>`、`<char3>` 可继续追加。没有 `<charN>` 时，把 `<角色手机>` 的直接内容视为单终端；没有 `<角色手机>`
外壳但含 App 标签时，可作为宽容兼容模式读取并记录警告。

### 8.2 解析与合并

- 初始化时扫描当前聊天的 assistant 消息，按楼层升序解析。
- 每个角色优先使用 `<status>` 中的 `角色ID` 作为稳定键，其次使用当前聊天身份注册表中已确认的角色名称映射；`<charN>`
  只表示本次输出顺序，不是跨楼层稳定 ID。
- 缺失角色 ID 和名称时，使用 `unknown:<message_id>:<charN>` 隔离为待认领终端，不得自动套用当前角色卡名称。
- 8 个 App 均视为“当前快照”：同一角色后出现的非空 App 区块覆盖先前区块。
- 单条消息只更新其中出现的 App；未出现的 App 沿用该角色上一次有效快照。
- 消息被编辑、重刷、删除或切换 swipe 时，从聊天记录重新构建，避免残留旧快照。
- 所有插入 DOM 的 AI 文本先进行 HTML 转义；仅允许明确白名单标记（如日历的 `<s>`），禁止脚本、事件属性、`javascript:`
  URL、iframe/object/embed。

### 8.3 手机私聊记录协议

副 API 私聊不强迫模型直接输出 HTML。模型返回经过校验的 JSON，渲染层再转换为组件：

```json
{
  "version": 1,
  "thread_id": "当前线程ID",
  "messages": [
    {
      "client_id": "模型本轮内唯一ID",
      "sender": "char",
      "type": "text",
      "content": "回复内容",
      "created_at": "2026-09-11T18:30:00+08:00",
      "payload": {}
    }
  ],
  "app_updates": {}
}
```

- `sender` 仅允许 `user | char | system`；副 API 通常只能生成 `char` 或必要的 `system` 事件。
- `type` 必须来自当前已启用的消息类型白名单；类型专属字段放入 `payload` 并按 zod 判别联合校验。
- `client_id` 只负责本轮去重，落库时由脚本生成全局唯一 `message_id`。
- `app_updates` 允许同一轮私聊顺带更新状态、备忘、空间、钱包、日历、浏览或音乐，但必须分别通过对应 App
  schema；校验失败时保留聊天回复并丢弃错误更新。
- JSON 外的解释、Markdown 围栏和思考过程均不入库；首次解析失败时可执行一次“仅修复格式”重试。

## 9. 全局脚本的卡片、聊天与 Char 隔离

### 9.1 三级命名空间

```text
card_key
└─ chat_key
   ├─ identity_registry
   │  ├─ char_key_a
   │  └─ char_key_b
   ├─ phone_snapshots
   ├─ threads
   │  ├─ thread:<char_key_a>
   │  └─ thread:<char_key_b>
   └─ ui_state
```

- `card_key`：优先采用酒馆当前角色/群组的稳定内部 ID；取不到时使用角色头像 ID 等稳定字段生成，不使用可被重命名的显示名称作为唯一键。
- `chat_key`：直接使用 `SillyTavern.getCurrentChatId()`；空值时禁止落库并等待聊天初始化完成。
- `char_key`：优先使用数据中的 `角色ID`；其次使用当前 `identity_registry`
  已登记映射；最后才由规范化角色名生成当前聊天内的键。
- `thread_id`：由 `card_key + chat_key + char_key` 确定，不能只有角色名。
- 内存缓存也必须使用完整命名空间；切换聊天时立即废弃旧请求序号和旧缓存引用。

### 9.2 单人卡自动建 Char

- 当前聊天尚无身份注册表，且只识别到一个明确角色时，自动创建恰好一个默认 Char。
- 默认 Char 的展示名可读取当前卡名，头像可读取当前卡头像；这是“单人卡初始化回退”，不是所有场景通用规则。
- 注册表保存 `source: auto_single_card`、卡片稳定 ID、创建时间和名称快照；卡片改名后更新展示名但保持 `char_key` 不变。
- 重载脚本、刷新页面或切换回同一聊天时复用原 Char，不得再次创建。

### 9.3 多人卡识别与隔离

出现下列任一信号即按多人模式处理：

- 同一有效数据块包含两个及以上 `<charN>`，且角色名称不同。
- 当前聊天已登记两个及以上 `char_key`。
- 输出显式声明多个 `角色ID` 或多个角色名称。
- 用户在身份管理中手动将当前聊天标记为多人模式。

多人模式规则：

- 只按实际角色 ID/名称创建 Char；角色卡显示名只作为“容器卡名称”显示，不创建同名 Char。
- `<char1>`、`<char2>` 只用于当前输出定位，解析后立即映射为稳定 `char_key`。
- 每个 Char 分别持有状态快照、私聊线程、草稿、未读、空间互动与生成锁。
- 名称冲突时展示来源提示并要求用户合并/拆分；在确认前保持两个隔离的临时身份，不擅自合并。
- 从单人误判转为多人时，若自动 Char 只是卡名占位且没有独立消息，可安全移除；已有消息时进入迁移确认，不静默删除。

### 9.4 每聊天独立存储

- 私聊消息、草稿、未读、置顶、虚拟转账状态、空间点赞和当前 Char 写入 `type: 'chat'` 的酒馆变量。
- 全局脚本变量只保存 UI 偏好与副 API 配置；不得保存可跨聊天复用的 `activeThread`、消息数组或剧情快照。
- 从正文解析出的 App 快照以当前聊天楼层为权威源，可在内存中索引，但聊天切换后必须重新读取。
- 副 API 请求发出时绑定
  `card_key/chat_key/thread_id/generation_id`；返回时再次核对当前命名空间，不匹配则丢弃 UI 写入并仅记录已取消。
- 删除聊天文件后不应在别的聊天展示其记录；不提供跨聊天自动迁移。手动导出/导入属于后续能力。

## 10. 酒馆消息衔接

### 10.1 初始化流程

1. 获取稳定 `card_key`、当前 `chat_key` 和最后楼层号；任一关键值未就绪时等待事件，不使用名称猜测。
2. 读取全局脚本设置，再读取当前聊天变量中的身份注册表、私聊线程与 UI 状态。
3. 用 `getChatMessages` 获取当前聊天的 assistant 消息。
4. 清空内存中的正文剧情快照，按楼层顺序解析并合并。
5. 判断单人/多人模式，执行幂等的 Char 自动创建或身份映射。
6. 合并正文 `<SNS>` 快照与当前聊天内的独立私聊记录，但保留二者来源标识。
7. 渲染手机，并根据设置决定发现手机格式或未读回复时是否自动弹出。

### 10.2 事件监听

至少监听并处理以下酒馆事件：

- `CHARACTER_MESSAGE_RENDERED`：增量读取新回复；必要时重新渲染楼层内的手机摘要。
- `GENERATION_ENDED`：仅处理酒馆主生成生命周期并同步最新正文输出；副 API 使用自己的 `generation_id` 状态机。
- `GENERATION_STOPPED`：解除对应的酒馆主生成锁，保留已完成数据。
- `MESSAGE_UPDATED` / `MESSAGE_EDITED`：全量重建。
- `MESSAGE_SWIPED`：全量重建当前分支。
- `MESSAGE_DELETED`：全量重建，移除已删除快照影响。
- `CHAT_CHANGED`：立即作废旧聊天请求、清空内存状态并加载新聊天的独立变量。
- `MESSAGE_SENT`：进入生成锁，避免重复触发。

所有 `eventOn` 返回的解绑函数统一保存，并在卸载时调用。额外 DOM 观察器仅作为事件遗漏的兜底，不作为主数据源。

### 10.3 发送桥接

- 默认路径：手机消息写入当前 `thread_id`，由独立生成适配器调用副 API，再把结构化回复写回同一线程。
- 同步正文路径：仅在用户主动开启后，使用 `/send 文本|/trigger`，行为参考 baibai_phone；此路径会触发酒馆主 API。
- 尾附路径：仅在用户主动选择后，通过酒馆页面的 `#send_textarea` 写入文本并派发冒泡的 `input` 事件。
- 发送前把手机输入转换为清晰的自然语言或结构化生成输入，不把 Vue 状态、HTML、API 密钥或其他聊天记录发给模型。
- 对正文桥接文本做换行、管道符和危险命令前缀处理，避免用户内容截断 STScript 命令链。
- 空消息、同线程生成中重复发送、缺失目标 Char、当前聊天已切换时禁止提交，并给出就地错误提示。

### 10.4 原始标签展示

- 默认不修改角色正则、不改世界书、不改聊天原文。
- 设置页可提供“隐藏聊天中的手机数据块”开关；实现时优先使用独立、可识别、可撤销的角色正则。
- 若提供“安装输出格式提示词/世界书”功能，必须由用户点击执行，并支持版本识别、预览、更新和卸载。

## 11. 独立副 API 生成

### 11.1 目标与默认行为

- 电波手机私聊默认通过酒馆助手 `generateRaw` 的 `custom_api` 调用独立模型，不读取或占用酒馆当前主 API。
- 默认禁止静默回退主 API。副 API 未配置、测试失败、超时或限流时，保留 User 消息为失败待重试状态。
- 用户可显式开启“失败时询问是否回退主 API”；每次回退都需要可见提示，不把它伪装成副 API 成功。
- 正文 `<角色手机>` 解析仍可独立工作，即使没有配置任何副 API，也能只读浏览 8 个 App。

### 11.2 Provider 与配置

首版支持酒馆助手 `custom_api` 已覆盖的三类来源：

- OpenAI-compatible：Endpoint、API Key、模型名。
- Google AI Studio：API Key，或代理地址、代理密码、模型名。
- Google Vertex AI：API Key/服务账号令牌、Location、Project ID、模型名。

设置页应提供：

- Provider 切换、命名配置槽、模型名输入、获取模型列表、连接测试与延迟反馈。
- `temperature`、`top_p`、`max_tokens`、frequency/presence penalty；不支持的参数不发送。
- 推荐起始值只作为可修改默认：`temperature 0.9–1.05`、`top_p 0.9`、单轮私聊 `max_tokens 800–1600`。
- API Key 使用密码框与掩码展示；日志、导出、错误消息和提示词预览不得出现明文 Key。
- Endpoint 只允许 `https`，本地开发地址需单独开启“不安全地址”开发选项。

### 11.3 请求组装

每次独立私聊通过 `generateRaw` 传入 `ordered_prompts`，建议顺序：

1. 电波手机总则与输出协议。
2. 当前角色卡中与目标 Char 有关的设定；多人卡时不得把容器卡名写成角色身份。
3. User 人设与双方关系信息。
4. 当前酒馆聊天的近期相关上下文，可配置最近 10–40 条。
5. 当前聊天、当前 Char 的手机 App 快照摘要。
6. 当前 `thread_id` 的手机私聊历史；默认最近 30–80 条，并保留被引用消息。
7. 本次消息类型、用户输入和目标动作。
8. JSON schema 与“只输出 JSON”的最终约束。

正文历史与手机私聊历史必须标记来源，避免模型把“正文中发生的事”和“手机里说过的话”混成同一场景。

### 11.4 生成状态机

- 每次请求生成唯一 `generation_id`，并绑定 `card_key/chat_key/thread_id`。
- 支持流式接收；流式内容只用于“正在输入”预览，完整 JSON 校验通过后才正式落库。
- 支持停止、超时、最多 1–2 次重试和切换副 API 配置重试。
- 首次响应格式错误时允许一次低温“格式修复”请求；不得把修复请求结果写入别的线程。
- 返回结果先经 JSON 提取、zod 校验、类型白名单和身份校验，再写入当前聊天变量。
- 模型若返回了非目标 Char 发言、User 代写、未知消息类型或危险 URL，拒绝对应消息并展示可诊断错误。

### 11.5 质量策略

- 每次请求只锁定一个目标 Char，保持该角色的措辞、关系、当下情绪与信息边界。
- 提供近期对话和长期摘要的分层上下文，避免无限塞入全部聊天导致角色重点漂移。
- 对重复句式、复读用户原话、连续追问、AI 助手腔和无依据情节推进设置明确负面约束。
- 不用更高温度代替角色资料；设定缺失时保持克制，不擅自补全关键身份和关系。
- App 更新与聊天回复分开校验；App 更新失败不应吞掉质量合格的对话回复。

## 12. 内置预设提示词

### 12.1 借鉴范围与排除项

内置预设借鉴“日月西糯叽机”的**写法**：模块化标题、短规则、优先级、执行项、禁忌项和明确输出格式。不得整体导入该 nuopreset，也不得把其框架元数据当成日月西正文。

明确排除：

- 所有 `type: "marker"` 的 `m_*` 块，包括 worldbook、soul、memory、context、thinking 等注入槽位。
- `[LOADING]`、随机校验串、预设头尾包装、thinking/Ecot 包装、授权/自审块。
- 与电波手机无关的越狱、NSFW、写作词库、模型人格宣言和采样参数。
- 原预设的 ID、key、injection、enabled 等 nuopreset 配置字段。

只保留以下风格原则：角色有自身动机、线上线下时空连续、信息有限、口语自然、关系动态、避免说教和 AI 助手腔、不要用无依据追问强迫用户继续聊天。

### 12.2 全局基础提示词

```text
[电波手机·生成总则]
任务：为当前聊天中的指定 Char 生成手机内容；只服务于 target_char，不扮演其他 Char，也不替 User 发言。

身份：
- target_card 可能是单人角色卡，也可能只是多人角色的容器。
- 以 target_char.id、target_char.name 和 target_char.profile 为准；禁止把角色卡名自动当成 target_char。
- 只使用当前 card_key / chat_key / thread_id 提供的内容，不引用其他聊天或其他 Char 的私聊记录。

连续性：
- 区分“酒馆正文事件”和“手机私聊事件”；两者可互相知晓，但不能混成同一句现场叙事。
- 保持时间、地点、关系、已知事实和角色语气连续；设定未提供的关键事实保持未知。
- 角色不是全知视角，只能依据自己经历、收到的消息和合理观察回应。

表达：
- 语言像真实的人在使用手机：允许短句、停顿、改口、少量表情与不完整句，但不能机械堆梗或故意难读。
- 角色有自己的生活、判断和情绪，不一味迎合，也不以说教、心理咨询或总结报告口吻回应。
- 不复述整段用户输入，不连续抛出问题，不用“某人/某位”代称 User；优先使用已知称呼。

安全与格式：
- 只输出要求的 JSON；不输出 Markdown 围栏、分析过程、前言或结语。
- 不生成脚本、HTML 事件、危险 URL、真实支付承诺或真实定位声明。
- 只使用 schema 允许的消息类型和字段；不知道的字段留空或省略，不编造资源 ID。
```

### 12.3 消息 App 提示词

```text
[电波手机·私聊回复]
目标：针对 User 最新一条手机消息，生成符合 target_char 的一轮私聊回复。

回复节奏：
- 默认生成 1–5 条消息气泡；简单问题可只回 1 条，情绪涌动或补充说明时再拆分。
- 单条以 2–35 个中文字符为常态，必要说明可更长；不要为了满足数量拆成无意义碎片。
- 不写第三人称动作旁白、场景描写或“角色回复：”；需要表现停顿可通过分条、标点或极短补充完成。
- 允许角色主动延伸一个与当下有关的话题，但禁止每轮结尾都追问。

人格与关系：
- 用角色惯用词、语气、称呼和幽默方式；亲密程度必须与当前关系一致。
- 先回应 User 真正表达的内容，再加入角色自己的反应；避免只给建议而没有情绪反馈。
- 角色可忙碌、迟疑、不同意或暂时不回某个问题，但要给出符合情境的反应，不能用系统式拒绝敷衍。

消息类型：
- 以 text 为默认；只有上下文确实触发且对应功能已启用时，才可使用 emoji、voice、image、transfer、location、link、call 或 system。
- emoji 只能使用 available_emoji_ids；没有匹配项就改用文字或 Unicode 表情。
- image/video 没有真实资源时只能给出 description，不虚构可访问 URL。
- transfer 必须符合虚拟钱包余额、币种与关系情境；不得暗示真实资金到账。
- call 只创建邀请/状态事件，不宣称真实音视频链路已经接通。

输出：严格遵循 PhoneChatResponse JSON schema；sender 只能是 char 或必要的 system。
```

### 12.4 状态 App 提示词

```text
[电波手机·状态更新]
任务：依据最新正文与私聊，更新 target_char 的状态快照。

规则：
- 好感指数表示长期关系倾向，普通一轮变化以 ±0–3 为常态；只有明确重大事件才允许更大变化，并给出简短原因。
- 性欲指数只反映当前情境中的身体/心理欲望，不等于同意，不自动推动亲密行为；无相关情境时保持或自然回落。
- 情绪气泡给出 1–4 个当下情绪词，允许矛盾并存，避免只写“开心/难过”的扁平标签。
- 隐秘心声是角色不会直接说出口的短想法，必须符合信息边界，不能泄露作者视角或系统规则。
- 器官状态只记录剧情明确涉及或当前显著感受的身体部位；不为凑数遍历全身，不无依据制造伤病。
- 所有变化与上一快照连续；信息不足的字段沿用旧值，不随机重置。

输出：只返回 status schema 字段，不附带剧情正文。
```

### 12.5 备忘 App 提示词

```text
[电波手机·备忘更新]
任务：生成或更新 target_char 私人备忘、清单与可选涂鸦。

规则：
- 只记录角色确实想记住、准备执行或反复惦记的事情；不要把正文摘要全部搬进备忘录。
- 每次新增 0–3 项，标题短而具体，内容包含可执行信息、私人语气或记忆线索。
- 已完成、取消或延期必须继承旧条目 ID 并更新状态，不能换个标题制造重复项。
- 可保留日常琐事、与 User 有关的计划和角色自己的生活事项，避免所有条目都围绕 User。
- 随性涂鸦为可选项；ASCII 必须短小可显示，解析只解释角色画了什么，不做过度心理诊断。

输出：返回 memo patch；无合理更新时返回空 patch。
```

### 12.6 空间 App 提示词

```text
[电波手机·空间动态]
任务：判断 target_char 是否会在当前时间发布动态，并生成自然的社交内容。

规则：
- 发布不是每轮必发生；没有分享动机时返回空更新。
- 动态从角色的生活、观察、兴趣、关系网络和当下情绪自然长出，不能变成给 User 的公开情书合集。
- 文案像真实社交平台内容，可短、含蓄、幽默或配一句图片描述；禁止上帝视角总结剧情。
- 可提及已知 NPC、同事、亲友或宠物，但必须遵守当前聊天已知关系，不混淆人物。
- 公开内容不得泄露角色明确想隐藏的私聊、隐秘心声或敏感身份信息。
- 点赞、评论数若无数据来源则省略；不要伪造精确的巨大热度。

输出：返回 0–2 条 zone post，包含稳定 post_id、正文、时间和可选媒体描述。
```

### 12.7 钱包 App 提示词

```text
[电波手机·钱包更新]
任务：根据已发生的虚构收支更新 target_char 钱包。

规则：
- 只有正文或私聊明确发生购买、收入、转账、退款等行为时才新增流水。
- 金额、币种、收支方向、商品和备注必须与事件一致；不知道金额时使用 unknown_amount，不凭空猜精确数字。
- 每笔流水生成稳定 transaction_id；重试生成不得重复记账。
- 余额 = 上一余额 + 已确认收入 - 已确认支出；待接收转账不提前计入余额。
- 钱包只表示剧情内虚拟资产，不声称真实法币价值或真实到账。

输出：返回 wallet transaction patch；无交易时返回空 patch。
```

### 12.8 日历 App 提示词

```text
[电波手机·日历更新]
任务：维护 target_char 已知的计划、约定、截止时间与完成状态。

规则：
- 只添加对话中已确认或角色明确决定的事项；模糊愿望不能自动变成确定日程。
- 明确日期按 ISO 时间输出；只有相对时间时保留 relative_time 和来源文本，不擅自换算错误日期。
- 事件需有稳定 event_id、标题、参与者、状态和来源；改期/取消更新原事件，不创建重复项。
- 线上聊天与线下见面必须保持时空连续，不能忘记距离、时区和已发生冲突。
- 天气只有上下文明确提供时才记录，否则为 unknown，禁止随机生成。

输出：返回 calendar patch；无变化时返回空 patch。
```

### 12.9 浏览 App 提示词

```text
[电波手机·浏览记录]
任务：生成 target_char 在剧情中合理产生的搜索或浏览记录。

规则：
- 只有角色存在明确疑问、兴趣、准备或查证行为时才新增记录，不为解释剧情强行搜索。
- 查询词应像真人输入，可简短、不完整、有个人习惯；结果摘要只写角色可能看到的内容。
- 不捏造可点击 URL、真实新闻结论、商品价格或医疗/法律权威答案；无可信来源时 source_type=local_note。
- 私密搜索可反映角色自身，但不能越过角色信息边界知道未被告知的秘密。
- 重复搜索可合并次数与最近时间，不复制大量相同结果。

输出：返回 browse history patch；URL 必须通过 http/https 校验。
```

### 12.10 音乐 App 提示词

```text
[电波手机·音乐更新]
任务：为 target_char 选择或记录当前合理的歌曲、歌词片段与收听状态。

规则：
- 选择应与角色偏好、情绪或剧情场景有关，不要每轮机械换歌。
- 对真实歌曲只使用上下文已给出的歌名、歌手和歌词；不确定时可生成“虚构歌曲”，并显式标记 fictional=true。
- 精选歌词最多 1–4 句，不输出长段受版权保护歌词；虚构歌词也保持简短。
- 没有真实音频 URL 时 playable=false，不伪造播放进度和时长。
- 一起听或分享歌曲必须由实际消息行为触发。

输出：返回 music snapshot 或空 patch。
```

### 12.11 跨 App 调度提示词

```text
[电波手机·更新路由]
先判断本轮事件影响哪些 App，再只调用必要模块：
- 关系或身体状态变化 → status
- 明确私聊发送/回复 → messages
- 记事、清单、约定前准备 → memo
- 公开分享动机 → zone
- 确认收支/转账 → wallet
- 确认时间安排 → calendar
- 明确搜索/浏览行为 → browse

限制：

- 每个 patch 独立校验；没有变化的 App 不输出。
```

## 13. 设置与持久化

使用 zod 分别定义全局脚本设置与当前聊天数据，并通过 `getVariables` / `replaceVariables` 按正确作用域持久化。

全局脚本变量建议包含：

- 手机显示/隐藏、悬浮入口位置。
- 自动发现格式后弹出、无格式时自动隐藏。
- 独立副 API / 同步正文 / 尾附输入框三种发送模式，默认独立副 API。
- 自动轮播开关、间隔与暂停状态。
- 字体模式、字号、可选自定义字体配置。
- 音乐界面样式。
- 是否在聊天显示区隐藏原始手机标签。
- 副 API Provider 配置、模型参数、重试/超时和是否允许询问后回退主 API。
- 各模块内置提示词版本、用户自定义补充词和恢复默认能力。

当前聊天变量建议包含：

- `identity_registry`、单人/多人模式和待认领身份。
- 私聊线程、消息、草稿、未读、置顶、引用和消息操作状态。
- 当前 Char、空间点赞、虚拟转账状态等当前聊天专属 UI/交互数据。
- 数据版本与迁移记录。

剧情快照、钱包金额、状态指数等不得写入脚本变量作为权威数据。

## 14. 错误处理与日志

- 顶层初始化使用 `errorCatched` 包装；不可恢复错误抛出 `Error` 并用 toast 提示。
- 关键日志统一前缀 `[wave-phone]`，包含初始化、聊天 ID、解析楼层数、终端数、事件名称与耗时。
- 不在生产日志输出完整隐秘心声、完整聊天内容或 API 配置，只记录长度、ID 和短预览。
- 解析失败按 App 隔离；错误卡片提供“重新同步”入口。
- 同步过程使用互斥锁或请求序号，后发同步结果覆盖先发结果，避免快速切换聊天时串数据。

## 15. 性能与兼容性

- 初次进入聊天允许全量扫描；普通新回复只增量解析最新楼层。
- 编辑、删除、swipe、聊天切换再进行全量重建。
- 频繁事件使用 100–300ms 合并/防抖，避免重复扫描与重复挂载。
- 设备切换、App 切换不重新解析聊天，只读取内存快照。
- 定时器、观察器、音频和事件监听均有明确释放路径。
- 兼容桌面与移动版 SillyTavern；不依赖 Node.js API或 Next.js 运行时。

## 2026-09-14：双触发模块生成与文中卡片（本轮新增）

### 产品目标
手机内容具备两种生成入口，两者共享内置电波手机规则和模块协议。
- **手动触发**：用户明确选择生成功能，直接发送内置手机边界、该模块规则和当前上下文。不得随机改为其他功能。
- **跟随酒馆**：在酒馆新一轮正文生成前按概率抽取允许的模块，将该模块提示词注入本轮主请求的聊天末端 system（depth=0）；正文正常生成，手机仅提交有依据的新内容。一次请求最多抽取一个模块，后续可扩展权重、冷却和多模块上限。
- **增量合并**：未提供的模块原样保留；状态为最新快照，备忘/日历/浏览/音乐追加新文本，空间动态与钱包流水依据稳定 ID 合并。手机消息依据来源楼层和内容 ID 去重；切换 swipe、编辑或删除来源楼层后重建对应来源消息。
- **文中 HTML**：特殊消息（转账、位置、拍一拍等）及其他 App 更新，在正文相关数据块位置生成展示卡片。模型输出结构化事件，脚本生成经过转义的 HTML，不直接执行模型提供的 HTML/JS。
- **不发送美化**：自动维护酒馆全局正则中的电波手机专用规则；仅格式提示词规则去掉标记包裹的 HTML；仅格式显示规则隐藏结构化数据。模型继续看到事件数据，页面展示卡片。保留其他正则，重复初始化不新增副本。
